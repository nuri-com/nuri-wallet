- Inventory rule: every source reference below is resolved against the exact release-source head, not this documentation branch. A different PR #857 head makes this manifest stale and requires a refreshed inventory before verification.
- Scope: client-reachable runtime network boundaries, including configured production, testnet, fallback, optional, migration-only, and transitive provider dependencies. Static links, build-only tooling, development-only endpoints, and removed code are accounted for separately.

Hosts are intentionally limited to host/provider identity and non-secret route families. Secret-bearing URL components, API keys, tokens, identifiers, and credentials are not reproduced.

## Classification vocabulary

| Classification | Meaning | Monitoring expectation |
| --- | --- | --- |
| `release-required` | A normal v0.88.0 user path depends on the service. | Safe read-only probe and alert unless authentication or protocol constraints require a synthetic/authenticated probe. |
| `conditional-required` | A shipped user path depends on it only for a selected network, platform, feature, route, or fallback. | Monitor when that condition is supported; keep environment and route separate. |
| `migration-only` | Reachable only by an explicit migration/recovery path. | Low-frequency safe reachability or authenticated synthetic probe; not core availability. |
| `retained-future` | Deliberately absent from this release but retained for an approved future product path. | Catalog without release alerting. |
| `gnosis-legacy` | Removed with the Gnosis Pay era and not required by v0.88.0. | Retain in catalog without v0.88.0 release alerting. |
| `excluded` | Not a runtime service boundary for release health. | Do not add a release-health probe. |

## Secret-safety finding

The exact release head contains credential-like material or secret-bearing URL components in client configuration, including RPC, mailer, and development/test configuration. This manifest deliberately records only provider/host identity and source location, never the value. Because Expo public/client bundles cannot provide server-side secrecy, credential owners should assess rotation, least privilege, quota controls, and migration behind Nuri-owned proxies in separate authorized work. This task neither changes nor validates credentials.

## Inventory conclusions

- Wirex is the active v0.88.0 card/IBAN partner. Production (`banking.nuri.com`) and testnet (`wirex.nuri.com`) are distinct boundaries and must never share one health state. On the PWA, both Wirex and SwapKit are direct cross-origin dependencies whose approved-origin CORS contract must be monitored; they are intentionally absent from the same-origin proxy used for sign/Arkade/node/FX.
- Gnosis Pay/card partner runtime code, Near/1Click direct paths and Monerium runtime code are absent at the exact release head. Gnosis Chain RPC is not legacy: SwapKit sweep/claim can still sign/broadcast a chainId 100 funds-recovery action and needs conditional critical RPC monitoring.
- Monerium is `retained-future` for planned business accounts and must never be classified `gnosis-legacy`.
- SwapKit is mainnet-only in the app. The complete generic sweep signer set is Ethereum (1), Base (8453), Arbitrum (42161), Optimism (10), Polygon (137), BSC (56), Avalanche (43114) and Gnosis (100): Base uses the configured Alchemy transport; every other chain uses the pinned viem 2.37.8 `http()` default recorded above. The app's separate `chainRpc` primary/fallback pairs are not signer failover; only the overlapping `polygon-rpc.com` and `arb1.arbitrum.io/rpc` endpoint health signals should be reused to avoid duplicate provider alerts. Downstream route providers remain dynamic/transitive and should be reconciled from safe quote/track schema evidence and the server catalog, not guessed into direct client endpoints. Missing CoW amount bounds fail closed, post-send Arkade tracking gets one in-session retry before durable hydration, and RPC readback failures after a journaled HTLC broadcast are not equivalent to a confirmed on-chain revert.
- Arkade has three separately meaningful availability domains: Nuri signer/API (including root LNURL alias and username availability), Arkade node/indexer, and Boltz. Arbitrary recipient-selected Lightning-address/LNURL domains and returned callbacks are a separate dynamic boundary; their failures must not be attributed to those three fixed services.
- Optional/configured boundaries must be resolved from approved release configuration without putting secret-bearing values in version control or OpsWatch.
